Deployment Notes

This page documents the durable operating model for Alfred University: static GitHub Pages hosting, local-first progress, optional Cloud Sync through a Worker/D1 backend, offline caching, and safe maintenance/recovery practices.

Architecture

Four layers with separate responsibilities.

Keeping these layers distinct makes maintenance and troubleshooting much safer.

1 · GitHub repository

The repository on main is the source of the static frontend. Website updates replace files at the repository root; no wrapper directory or frontend compilation step is required for normal content/runtime releases.

2 · GitHub Pages

GitHub Pages publishes the static HTML, CSS, JavaScript, documents, images, manifest, and service worker over HTTPS. A successful repository upload is not fully verified until the Pages build/deploy run succeeds for that commit.

3 · Browser / local state

Academic progress is local-first. The browser stores progress and the Cloud Sync configuration locally. Clearing site data can therefore remove unsynchronized local state and should not be used as a routine refresh technique.

4 · Optional Cloud Sync

When connected, the browser sends progress records through the configured HTTPS Cloudflare Worker to its D1 database. The website and Worker must agree on the Cloud Sync protocol reported by build-info.json.

Cloud Sync Operations

Progress owns setup, connection state, and recovery credentials.

Deployment Notes explains the architecture; Progress is the interface that actually connects or tests it.

What the browser keeps

  • Course progress in local browser storage.
  • The configured Worker root URL.
  • The private Student Sync / Recovery Key.
  • A per-browser device ID and device name.
  • The last successful sync timestamp.

The static website does not embed a master database password or a conventional account login.

What a sync checks

  • Worker health endpoint is reachable over HTTPS.
  • D1 database binding is available.
  • D1 schema reports ready.
  • Worker protocol matches the website protocol.
  • Progress records merge by record timestamps instead of blindly replacing the whole local state.

Offline & Service Worker

Offline support is a convenience layer, not the deployment source of truth.

The current service worker uses a versioned cache and separates runtime verification from offline content.

Network-first code

HTML, CSS, JavaScript, web manifest files, and page navigations try the network first and fall back to cached copies when the network is unavailable.

Versioned cache

Every runtime release changes the service-worker cache namespace. Activation removes older Alfred cache namespaces so the browser does not keep serving an obsolete application shell indefinitely.

Build marker stays live

build-info.json bypasses the normal offline cache path. Use it when deciding what release is actually deployed.

Installable web app

The HTTPS site includes a web-app manifest and can be installed or added to a device home screen. Installation does not change where progress or Cloud Sync data is stored.

Safe Maintenance & Recovery

Protect progress before changing infrastructure.

Use the lowest-risk recovery step first. Do not destroy local state to solve an ordinary cache or deployment problem.

  1. Before major maintenance: export Progress and keep the Student Sync / Recovery Key separately.
  2. After a site update: confirm GitHub Pages deployed the intended commit, then check build-info.json for the expected runtime/build.
  3. If the browser looks stale: reload normally first. The network-first application files and versioned service-worker cache are designed to update without clearing site data.
  4. If Cloud Sync fails: use Progress to inspect the configured Worker URL, connection state, and health/protocol errors. Do not generate a new key merely because the server is temporarily unreachable.
  5. If changing the site origin/domain: treat it as a new browser origin and make sure the Cloud Sync backend allows that origin before relying on sync there.
  6. Do not clear browser site data as a routine fix. Local-only or not-yet-synchronized work can be lost.
